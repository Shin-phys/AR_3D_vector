# 運動ベクトル可視化（3D／AR）

高校物理向け。生徒が撮影した動画から **3D の軌跡を復元し、空間に固定した3Dストロボとベクトルを回り込んで見る**ための教材。
2D 版（[Hodograph](https://github.com/Shin-phys/Hodograph)）の姉妹アプリ。

| | 2D（Hodograph） | 3D（このリポジトリ） |
|---|---|---|
| 生徒がすること | **自分で矢印を描く** | **視点を動かして観察する** |
| 到達点 | Δv を作図して加速度の向きを自分で見つける | 空間での向きと、影・成分を見る |
| 核になる教材 | 速度ゼロでも加速度はある | **円運動の影が単振動になる** |

仕様は [`docs/3D仕様.md`](docs/3D仕様.md)。このリポジトリで仕様から変えた点は、この README の「仕様から変えたこと」と仕様書の §12 にある。

## 使い方（開発）

ビルドは不要。GitHub Pages でそのまま配る。

- `index.html` … 共有用の入口（https://shin-phys.github.io/AR_3D_vector/）。3d.html へ送るだけ
- `3d.html` … 本体。お手本（合成のターンテーブル動画）で最後まで試せる
- `ar-test.html` … フェーズ1。**iPhone の Safari で開いて**、4つの方式のどれで AR が開くかを確かめる
- ローカル確認：`python3 -m http.server` で開く（AR は https が要るので実機は Pages で）

### テスト

```bash
node tools/test/run.js            # 計算のテスト＋ブラウザのテスト（Playwright）
node tools/test/run.js --shots    # スクリーンショットも tools/test/out/ に残す
```

Playwright はリポジトリに入れていない（依存ゼロの方針）。手元で走らせるなら `npm i -D playwright` を一度。
見つけ方は `tools/test/pw.js`。

| ファイル | 中身 |
|---|---|
| `unit.js` | 合成データで受け入れ条件（半径 3% 以内・Δv の向き ±5°・影の周期・座標系の向き）。ブラウザ不要 |
| `e2e.js` | お手本動画で、生徒と同じ操作を最初から最後まで（タイル→トリム→四隅→色→追跡→使うコマ→3D→予測→影）。スマホ幅と PC 幅の2通り |
| `ar.js` | `ar-test.html` が開き、GLB と USDZ が作れるか |

**共有モジュールを取り込み直したら、必ず走らせること。**

## 変えてはいけない約束

### 1. 共有モジュールはこのリポジトリで編集しない

`SHARED.txt` に並んだファイルは Hodograph のコピー。**直すときは Hodograph 側で直して、取り込み直す。**

```bash
sh tools/sync-shared.sh ~/Webアプリ開発/ホドグラフ
node tools/test/run.js
```

仕様書は「同じリポジトリの別ページ」だったが、運用の都合で別リポジトリにした。仕様書が同じリポジトリにした理由
（**書き写すと、2つの追跡が別々に育つ**）はそのまま残るので、それをこのルールとテストで抑えている。
`SHARED.txt` には取り込んだ時点の各ファイルの md5 を書いてあるので、手で触ったかどうかは比べれば分かる。

### 2. 座標系（3D仕様.md §3、ただし x の取り方を補った）

右手系。**y＝鉛直上、x＝画面の右、z＝カメラ側（手前）**。単位は m・s。原点は紙の角 A（1つ目に押した角）。

x を紙の辺ではなく「画面の右」に合わせているのは、**どの角から押し始めても 3D の向きが動画とそろう**ようにするため。
紙の上で画面の右に当たる向きは射影変換だけで決まる（焦点距離にも姿勢にも依らない）。鉛直軸まわりに回すだけなので、
水平・鉛直は変わらず物理は何も変わらない。鏡像にならないよう、押した順が画面の上で時計回りかどうかで z の符号を決めている。
テスト：「押し始める角4通りとも、カメラが +z 側」「時計回り／反時計回りに押しても回転の向きが同じ」。

### 3. 半コマずれ（2D と同じ）

```
位置    r₀      r₁      r₂      r₃
速度       v₀.₅    v₁.₅    v₂.₅
Δv             a₁      a₂
```

`HG.kin3d.v[k]` は r_k → r_{k+1}、`HG.kin3d.a[k]` は **r_{k+1}** に置く。2D とずらすと、同じ動画で 2D と 3D の矢印が1コマずれる。

仕様書の `HG.kin3d = [{t, vx, vy, vz, ax, ay, az}]`（1本の配列）は **`{v:[…], a:[…]}` の2本に分けた**。
速度と加速度は属する時刻が半コマずれるので、同じ行に並べると必ずどちらかが嘘になる。

### 4. モデルを当てはめない・平滑化しない

円も正弦波も当てはめない。壁の影のグラフも、測った点を順に結んだ線だけ（曲線は重ねない）。
**当てはめで出した加速度を矢印として見せた瞬間に、教材の根が切れる**（3D仕様.md §4）。

### 5. ビューアと AR は同じ中身を使う

3D の中身は `content.js` が1か所で組み立て、ビューアも AR も同じ Group を使う。別系統にすると、AR でだけ矢印の位置や倍率が食い違う
（2D の「別系統の描画を作らない」と同じ理由）。
**部品は全部「面（Mesh）」で作る。** 線（Line）は USDZ に載らないので、AR でだけ目盛りや矢印が消える。
文字も 3D の中に入れない（HTML で重ねる）。

### 6. ボタン名・ガイド文に結論を書かない

「影は単振動」ではなく「奥の壁に影を落とす」。解説（`preset.note`）は **Δv と壁の影の両方を生徒が自分で出したあと**にだけ出す。
`shootTips`（撮影の注意）は解析の前に出るので、答えを書かないこと。

### 7. ✓ は生徒の行為にだけ付ける（2D の罠）

ステップ6の ✓ は「3D で見る」を**押した**ときに付く。アプリが自動で開いても付けない。ステップ2は四隅から射影変換が解けたとき。

### 8. 貼り付くブロックに何も足さない（2D の罠）

スマホでは、3D の画面は動画のキャンバスと**入れ替える**（同じ高さの予算＝画面の 42%）。グラフや操作は下のカードに置く。
実測（390×844）：3D を開いたときの貼り付くブロックは画面の 41%。

### 9. 視点は瞬間移動させない

視点の切り替えは注視点のまわりを 0.9 秒かけて回る。**最初に開いたときは「撮影位置」から始めて「斜め」へ回り込む**ので、
3D の点が動画のどの点かを見失わない。

## 仕様から変えたこと（理由つき）

| | 仕様書 | ここでの実装 | 理由 |
|---|---|---|---|
| 置き場所 | 同じリポジトリの別ページ | **別リポジトリ**。共有モジュールはコピーし、同期スクリプトとテストで縛る | 運用の都合（ユーザーの判断） |
| x 軸 | 「画面右」 | **紙の上で画面の右に当たる水平の向き**（射影変換から） | 押し始める角に依らず、3D の向きが動画とそろう |
| `HG.kin3d` | 1本の配列 | **`{v, a}` の2本** | 速度と加速度は属する時刻が半コマずれる |
| Δv の矢印 | （記述なし） | **速度の差 × Δt**（変位の差ではない） | スマホの動画は VFR。変位の差は Δt の不揃いぶん傾く（合成データで最大 4.85° → 4.00°） |
| 焦点距離 | （記述なし） | **推定しない**。標準カメラ（横の画角 69°）で置く | 四隅が σ=2 px ずれるだけで、推定値が真値の 0.57〜3.4 倍に散った（40通り）。撮影ガイドに「標準カメラ（1×）で撮る」を入れた |
| 長い辺／短い辺の取り違え | （記述なし） | **押した後に各辺へ寸法を書いて生徒が確かめる**＋「入れ替える」ボタン | 画像から見抜く案は、上と同じ理由で当たらなかった |
| 精度の見積もり | 2 px ÷ 長い辺 | **2 px ÷ 短い辺**（悪いほう） | 斜めから撮ると奥行き方向の辺が縮んで写り、そちらのほうが効く |
| 床の描き方 | — | **球の半径だけ下げて描く**（測った座標は y=0 のまま） | 紙の面にそのまま描くと球の下半分が埋まって見える |
| AR の動き | 入れない（互換性優先） | **「いま」の球と影が測った軌跡をたどる**。速さ ×1〜×0.1 を書き出すときに決める | 実機で「静止画の影は、何を読み取るかが人それぞれ」と分かった（ユーザーの判断）。USDZ は書き出したあと model.usda に timeSamples を書き足す。GLB は AnimationClip |
| 軸の置き場所 | 原点（紙の角 A） | **部屋の隅（奥の壁と横の壁が出会う床の角）に、灰色の細い「向きの印」として置く**。位置ベクトルの基準は角 A のまま（小さな黒い印と「A（基準点）」） | 角 A は運動のすぐそばで、軸が Δv と重なった（実機）。円の中心は当てはめが要るうえ、Δv が全部軸を向く絵になって答えが先に見える |
| 斜方投射 | 4-B（見かけの大きさから奥行き）で | **鉛直な面の 4-A**：ボードに紙を貼り、紙の近くに吊るした糸で鉛直を決める。4-B は当面作らない | 4-B は誤差が大きい割に奥行きのある投射しか扱えない。ボードなら影（床＝水平は等速、横の壁＝鉛直投げ上げ）で教科書の分解がそのまま見える（2026-10-13 に決めた） |
| 成分分解 | 成分の矢印 | **矢印にも影を落とす**（速度・Δv を床と壁へ） | 影という1つの言葉で、位置も速度も加速度も読める。投射の Δv の床の影はほぼ点になる |
| 3D ホドグラフ | 作る | **作らない（未決に戻す）** | 紙の方式で測れる運動はすべて平面の中なので、2D のホドグラフと同じ図にしかならない |
| 机上サイズ | 1/5 | **中身の横の広がりが約 45 cm になる倍率**（ターンテーブルで ×0.9） | 1/5 では「小さめ」（実機） |
| Δv の倍率 | — | **×0.1〜×8**（1倍未満も） | お手本の円運動では実寸の Δv が長すぎた（実機） |
| AR ボタン | 3D ビューアに付ける | `ar-test.html` で方式を決めてから付けた。**iPhone は model-viewer を読まない** | 実機で方式3（blob の USDZ）が通ったので 1 MB を省ける |

## 鉛直な面（ボードに沿った投射）

- 「2. 紙の四隅」で面を選ぶ：**机・床（水平）**／**壁・ボード（鉛直）**。投射のタイルは鉛直、ターンテーブルは水平、自由測定は生徒が選ぶ
- 鉛直な面では、**糸の上と下の2点**を押して「下」を決める（糸は本物の鉛直なので、アプリが下を仮定せずに済む）。
  押さなければ画面の下を下とみなし、その旨を出す
- 座標：x＝水平・画面の右、y＝鉛直上、z＝ボードから手前。運動は z = 0 の面の中
- 影は「床」と「横の壁」。奥の壁＝ボードそのものなので出さない
- グラフは床の影の x（水平）と横の壁の影の y（鉛直）

### 測ったこと（合成データ、tools/test/unit.js）

| 条件 | 結果 |
|---|---|
| 正面 1.6 m・仰角 8°、基準は模造紙の半分、5点 | Δv の向き 最大 0.56°、水平の速度のばらつき 0.79%、Δv÷Δt＝9.91 m/s² |
| 横から 25°・仰角 15° | 最大 2.24° |
| ボールがボードの手前 3.5 cm を飛ぶ | 向き 最大 0.76°、g＝10.00（見積もり 9.8×1.6/1.565＝10.02 と一致） |
| スマホを 4° 傾けて構えた | 糸あり 最大 0.87° ／ **糸なし 最大 4.32°** |
| **基準の大きさ**（5点・40通りの中央値） | **A4：5.0° ／ 模造紙の半分：1.5°** |

**基準が軌道より小さいと、紙の外で誤差がふくらむ。** 四隅の数 px のずれが、紙の外へ引き伸ばされるため。
投射の軌道は A4 の約3倍に広がるので、撮影ガイドで大きな紙を勧め、3D を開いたときに軌道が紙の 1.8 倍を超えていたら知らせる。

お手本（合成）は 30 fps。60 fps で作ると、headless の Chromium の走査でコマが落ちた（56 コマ中 44）。実機の撮影は 60 fps を勧めたまま。

## 踏んだ罠

| 罠 | 中身 |
|---|---|
| **四隅から焦点距離を推定した** | 理屈では出るが、四隅が 2 px ずれるだけで 0.57〜3.4 倍に散る。f を使う機能（撮影位置から見る・辺の取り違えの検出）が全部不安定になった。f は撮影ガイドで固定する |
| **姿勢の直交化で r1 と r2 を取り違えた** | `cross(n, m)` だと二等分線から r2 の側へ回る。`cross(m, n)` |
| **ルーペが照準の十字ごと拡大する** | 太い十字を描くと、拡大像の中で角そのものが隠れる。中心を大きく空けた細い十字にした |
| **サムネイルが空になる** | WebGL は描いた直後でないと `toDataURL` が空（preserveDrawingBuffer を切っているため）。描いてすぐ取る |
| **iPhone は WebM を読めないことがある** | お手本は MP4（H.264）と WebM の2本を埋め込み、`canPlayType` で選ぶ。テストの Chromium は H.264 を持たないので WebM |

## 既知の小さな食い違い（共有モジュール側で直すもの）

- 投射のお手本（区間 14 コマ）で、ステップ5に「この素材では、どの間隔でも Δv がジッタと同じくらいの大きさにとどまります」と出る。
  `selection.js` の判定が「Δv が5本は残る範囲」を前提にしていて、コマ数の少ない素材では最初から満たせないため。
  3D では向きは最大 0.7° で問題ない（e2e の実測）。Hodograph 側で、点の数が少ないときの判定を見直すとよい。

- 手で打つ（ステップ4の B）を打ち終えると「ステップ4は済んでいます」と出る（2D の番号）。3D ではステップ5。
  文言が `track-controls.js`（共有）に書かれているため。Hodograph 側で番号を `HG.steps` から引くようにすれば直る。
- 同じく、打ち終えたあとに `#strobeCard`（2D のステップ5）へ飛ぼうとする。3D には無いので何も起きない（害は無い）。

## AR の確認結果（ar-test.html）

仕様書で「かなり怪しい」とした**方式3（blob URL の USDZ を Quick Look へ）が iPhone で通った**。色・形の崩れの報告も無い。
→ `3d.html` の「AR で見る」はこう作った（`panel3d.js` の AR の節）：

| 端末 | 開き方 |
|---|---|
| iPhone・iPad（Quick Look あり） | いま表示している中身から USDZ を作り、blob URL のまま Quick Look へ。model-viewer は読まない |
| Android（WebXR あり） | GLB を作って model-viewer に渡す。AR は指で押さないと始まらないので、生徒は model-viewer の右下の AR ボタンを押す |
| どちらも無い | AR の欄ごと出さない |

- 中身はビューアの表示そのもの（速度・Δv・壁の影の ON/OFF がそのまま入る）。「いま」の球は入れない
- 既定は**机上サイズ**（中身の横が約 45 cm になる倍率。指で拡大縮小も可）。実寸は拡大縮小させない
- **「いま」の球と影を動かす**（既定 ON）。速さは再生の速さ（×1／×0.5／×0.25／×0.1）と同じ値を書き出すときに焼き込む。
  Quick Look には再生速度のつまみが無いため。USDZExporter は動きを書かないので、出てきた `model.usda` に
  `xformOp:transform.timeSamples` を書き足して詰め直している（`ar.js addUsdAnimation`）。
  書き出した USDZ を usd-core（Pixar の USD 0.26.8）で開き、3つの部品に 52 個ずつ時刻があることを確かめた。
  **Quick Look で実際に動くかは実機待ち**
- **USDZ を作るのに 0.9 秒以上かかったら自動では開かない**。Safari は押した直後でないと Quick Look を開かないことがあるので、
  そのときは本物の `<a rel="ar">` を出してもう一度押してもらう（ar-test.html の方式3は数百 ms で作れて通った。壁や矢印を全部出すと重くなる）
